# Feature-centered testing

The test catalog at `tests/support/catalog/test-catalog.json` is the declarative source of truth for classification, selection, Feature lifecycle, test enforcement, duration budgets, methodology, and source files. Every test command validates that catalog and the fixture manifests through `tests/support/validation/foundations.ts` before execution. Permanent catalog test identifiers use `FBT`, `FST`, `CCT`, or `SST` plus a number, such as `SST-001`, and must match that test's category. They are catalog labels, not HTML id attributes. Example identifiers keep the `E` form, such as `FBT-E001`. `npm run test:view-test-catalog` creates `.test-results/catalog.html`, a static human-facing view that never executes tests. The page shows Feature Set, Feature, and Feature Behavior Tests, with Critical Core collapsed by default. Supporting Tests are intentionally absent from this page. Opened rows label lifecycle, enforcement, scope, environment, and browser mode separately, and contain a Test methodology disclosure that is closed until opened. Its primary result is the effective catalog state: disabled, deprecated, and retired override a stored execution, and a missing execution is unexecuted. A stored execution on those entries is secondary evidence, such as `last execution: passed`. A stored result with no test-definition fingerprint, or a fingerprint that does not match the current definition, is also unexecuted stale evidence and is never the current Passed result. That fingerprint covers the catalog test identifier, name, methodology, category, owner and associations, scope, environment, browser mode, regression, bug reference, root cause analysis, enforcement, duration budget, and source file. A release-gate result stays current only when its required-gate definition fingerprint still matches the required Feature Behavior and Critical Core definitions. Recording a run drops result entries whose identifiers are no longer in the permanent test catalog. Active required and nonblocking tests still show a truthful passed result when the fingerprint matches, and the advisory badge stays separate from that result.

The current page entries are runner-shaped TypeScript examples. An example uses an `E` in its identifier, such as `FBT-E001`, is labeled Example, and lives only in the `examples` list. Browser examples use `.example.spec.ts`; non-browser examples use `.example.test.ts`. Playwright and Vitest explicitly exclude those suffixes, so examples are not discovered, executed, reported as skipped, or included in the release gate. Their `test.skip`, `describe.skip`, or `it.skip` declarations make the illustrative runner shape recognizable without making the files executable tests. Examples do not protect the application or reserve later release identifiers such as `FBT-001`.

Promotion is deliberate: obtain approval for the permanent test identifier, sentence, methodology, protected behavior, assertions, classifications, duration budget, and target folder; replace declarations and illustrative seams with real production imports and approved test infrastructure; rename the file to the repository's executable runner convention; move its metadata from the `examples` list to the `tests` list; then verify focused discovery and the relevant broader commands.

## Baseline Feature Behavior Tests and Bug Checks

A baseline Feature Behavior Test checks for the presence of desired behavior. Its catalog fields are `regression: false`, `bugReference: null`, and `rootCauseAnalysis: null`.

A Bug Check is a classification on a Feature Behavior Test, stored as `regression: true` and displayed as Bug Check. It is not an organizational category and not a result state. It checks for the absence of one known or likely bug. Passing means that bug's user-visible behavior was not observed under the documented test methodology. One Bug Check covers one bug. Catalog validation requires the nonempty fields below and does not try to count bugs inside the text.

Every Bug Check requires a nonempty `bugReference` and a nonempty `rootCauseAnalysis`. Root cause analysis is stored separately from `methodology`. The viewer shows a static Bug Check badge, with the words Bug Check, next to the result mark. It is metadata, not a button. An opened Bug Check has two collapsed disclosures, in this order: Test methodology, then Root Cause Analysis. Test methodology renders only `methodology`. Root Cause Analysis renders only `rootCauseAnalysis`. A baseline test shows Test methodology only, with no Bug Check badge and no Root Cause Analysis disclosure.

When safe and practical, prove a Bug Check with a Bug Reproduction Run: the test fails for the intended behavioral reason in a safely restored bug-producing environment, then passes in the fixed environment. That run is review evidence only and never replaces the recorded release result. Remove the bug-producing environment after review unless continued maintenance is explicitly approved.

## Commands

Run these commands from the repository root. The browser application package does not own test scripts.

- `npm run test:view-test-catalog` writes `.test-results/catalog.html`, serves it at `http://127.0.0.1:4174/` (the next free port if that one is busy; set `TNC_CATALOG_PORT` to change the preferred port), and opens that page. Ctrl+C stops the server. `--no-open` serves without launching a browser; `--no-serve` writes the file and exits. The page shows Feature Set, Feature, and Feature Behavior Tests, with Critical Core collapsed by default. Supporting Tests are intentionally absent from this page. Each opened baseline test keeps Test methodology collapsed until it is opened. A Bug Check also keeps a separate Root Cause Analysis disclosure collapsed, directly after Test methodology, and shows a static Bug Check badge next to the result mark. Example entries are labeled Example and do not run. It does not execute tests. The header lists the latest command, its selector when present, how many tests that command ran, that command's status, and its total wall-clock time, then states the release-gate status on its own and says the gate was not rerun when the latest command was not a gate.
- `npm run test:fast-only`runs non-browser tests explicitly marked`fast: true` and reports exclusions.
- `npm run test:features` runs enabled Feature Behavior Tests, including nonblocking tests, and excludes Supporting Tests.
- `npm run test:core` runs enabled Critical Core Tests.
- `npm run test:shared` runs enabled Shared Supporting Tests.
- `npm run test:browser-deterministic` uses controlled inputs. Deterministic specs import `tests/support/browser/deterministic-network.ts`, whose automatic fixture fails unexpected external requests. Same-origin recorded fixtures and mocks stay allowed. `deterministicRequestAllowlist` in `playwright.config.ts` is the explicit external exception list.
- `npm run test:browser-live` runs the approved live-service browser project with up to three workers. Tests in one file stay in order; separate files can run together. They share one local page server.
- `npm run test:refresh-map-cache` deletes saved Esri and USGS 3DEP responses and runs every live browser test, which downloads them again. Use it in a fresh clone if you want a clean capture, or occasionally to catch an upstream Esri change such as transparent coastal tiles, since saved tiles otherwise hide such changes. A fresh clone does not need it: the first live run fills the cache.
- `npm run test:browser-all` and `npm run test:browser-only` run both browser modes.
- `npm run test:gate` uses the shared release-gate function: required Critical Core first, stop on failure or inconclusive verification, then required Feature Behavior Tests, including live tests. Supporting Tests stay outside the gate. An empty Critical Core phase is allowed when required Feature Behavior tests exist. When the catalog has zero required Feature Behavior and Critical Core tests, the gate is inconclusive, exits with code 2, explains that no required tests are configured, and does not report or store Passed.
- `npm run test:all` runs every enabled test plus linting and reports release eligibility separately from diagnostic health. When zero required tests exist, release eligibility is inconclusive and not verified. Diagnostic health still reflects the executed tests and lint on their own.
- `npm run test:feature -- F-110` runs enabled tests owned by or additionally associated with one Feature. Passing a catalog test identifier instead, such as `npm run test:feature -- FBT-133`, runs that one test even when it is disabled.
- `npm run test:id -- FBT-133` runs that one catalog test, including a disabled test. Feature commands, `test:all`, and the release gate still skip disabled tests.
- `npm run test:feature-set -- FS-100` runs enabled tests associated with one Feature Set.

Two opt-in flags let you watch browser tests. Either flag may come before or after the selector.

- `--headed`, such as `npm run test:id -- FBT-010 --headed`, opens visible browser windows, one per worker. Selection, projects, worker count, retries, and recorded results are unchanged. `test:gate` accepts it and warns that headed runs are slower. A command that selects no browser tests prints that the flag has no effect.
- `--ui`, such as `npm run test:id -- FBT-010 --ui`, opens Playwright UI mode for the same selected browser tests, including a disabled test named by identifier. UI-mode results are never recorded and never count toward release. `test:gate` rejects `--ui`, and so does a command that selects no browser tests.
- `--autorun`, such as `npm run test:id -- FBT-010 --ui --autorun`, also presses Playwright UI mode's Run all button as soon as the window opens, so the test plays in the UI at once. It needs `--ui`. The runner serves the UI with `--ui-port=0`, opens it in a Chromium app window, and clicks Run all. It sets `COPILOT_CLI=1` for that process, which makes Playwright skip opening its own browser tab. The catalog's Run in Playwright button uses this.

Before a non-empty batch starts, the command prints how many tests are about to run, the maximum duration, and the worker count. The maximum duration is the sum of those tests' duration budgets, in seconds, or in minutes and seconds once it reaches a minute. Live browser tests use the 3 workers configured for that Playwright project. Deterministic browser tests use 1 worker. Non-browser tests use Vitest's non-watch forks cap: one fewer than the machine's available processors, and at least one. In an interactive terminal, an animated spinner and `0 / N tests complete` status share one in-place line; each completion rewrites that line with the test identifier, outcome, and summed duration budget of the tests still unfinished (`Up to … remaining`). Only the final status line remains after a successful batch. Redirected and continuous integration logs stay append-only, with no cursor-control codes. That remaining figure is a ceiling, because workers can run tests at the same time. Scene measurement logs stay out of this live log. Failures and retry notices remain as permanent diagnostic lines. A live test with a retry left counts as complete only on the final attempt. The closing catalog report is unchanged.

A browser test's result is its final attempt. When that attempt passes and an earlier attempt failed, timed out, was interrupted, or was inconclusive, the stored state is `passed`, with `passedAfterRetry: true` and a `failedAttempts` list (attempt number, status, the first 20 error lines, location, stdout and stderr tails, and artifact paths). That pass counts for the command status, `npm run test:gate`, and `test:all` release eligibility. `durationMs` is the final attempt, and duration-budget warnings use that value. `totalDurationMs` is the sum across attempts. When the command finishes, the console prints each permanent catalog test in category order. The first line of an entry is the identifier, the final-attempt duration in seconds when it ran, and the result. The title wraps underneath at word boundaries. A passed entry, including a pass after retry, is green for every line. An entry that ran and did not pass, including a failure and an inconclusive result, is red for every line. An entry this command did not run is dark gray for every line. A pass after an earlier failed attempt reads `PASSED after retry`. Tests this command did not run, including Supporting Tests left out of a release gate, read `NOT RUN`. The list is followed by how many Feature Behavior Tests passed out of the catalog total, then how many Feature Behavior, Critical Core, and Supporting Tests were not run. `Total time` is the command's wall-clock duration. A `PASSED AFTER RETRY` detail line still names each failed attempt, and the catalog shows a Passed after retry badge with those details collapsed. There is no separate `flaky` state. Playwright's truncating line reporter stays off so those titles are not cut to the terminal width.

A stored result that failed, was inconclusive, or passed after retry also carries a `failureLog`: the attempt number and status, the ANSI-free error message without stack frames (up to 40 lines), the failing `file:line`, up to 12 repository stack frames (no `node_modules` or Node internals), stdout and stderr tails (40 lines), the screenshot, trace, and Playwright page-snapshot paths, the command that ran it, the run id (the `raw-*` report and `playwright-artifacts-*` key), and the time. Each text field is capped at 4000 characters. A failed or inconclusive result logs its final attempt. A pass after retry logs its last failed attempt. Vitest failures log the message and stack; they have no artifacts. The catalog page adds an Error logs disclosure, collapsed by default, after Test methodology and Root Cause Analysis on any such row. It shows a short header, the error, location, stack, and output tails in monospace blocks, and links to the screenshot, trace, and page snapshot. Copy for LLM copies one Markdown block with the identifier, title, methodology, error details, artifact paths, and `npm run test:id -- <ID>`. When the browser blocks the clipboard, the block is shown selected for a manual copy. A result recorded before error logs existed is rebuilt from the newest matching `raw-playwright-*.json` and labeled as rebuilt. While `npm run test:view-test-catalog` is serving, Open trace runs `npx playwright show-trace` on that row's stored trace, and Replay in Playwright UI runs `npm run test:id -- <ID> --ui`. Both start detached and write output to `.test-results/catalog-launch-logs/`. The server accepts only `POST /api/open-trace` and `POST /api/replay-ui` with a JSON catalog test identifier, from its own loopback origin. It looks up the trace itself and accepts only a `trace.zip` inside `.test-results/`. It never takes a command or path from the page. Open trace is disabled when no trace was saved. Replay is disabled for non-browser tests. The static `--no-serve` file still shows the logs and the copy button.

Required inconclusive verification exits with code 2, including a catalog that has no required tests configured. Failure exits with code 1. A passed gate exits with code 0. Local results are ignored by Git, with the latest observations in `.test-results/latest.json` and up to 20 command runs in `.test-results/history.json`. Each stored test result includes the test-definition fingerprint, and a gate result includes the required-gate definition fingerprint. Failed-attempt traces and screenshots stay in that run's `.test-results/playwright-artifacts-*` directory. Playwright 1.64 `trace: 'retain-on-failure'` keeps a failed attempt's trace when a later retry passes, `screenshot: 'only-on-failure'` writes the screenshot on the failed attempt, and `preserveOutput: 'always'` keeps the attempt directory.

## Lifecycle and enforcement

Feature lifecycle (`active`, `deprecated`, or `retired`) and test enforcement (`required`, `nonblocking`, or `disabled`) are independent catalog fields. Legal combinations follow category semantics:

- Critical Core Tests use `required` enforcement.
- Active Feature Behavior Tests default to `required`. A `nonblocking` or `disabled` exception needs approval evidence.
- Deprecated Feature Behavior Tests may stay `required` or, with explicit approval metadata, use `nonblocking` or `disabled`.
- Feature Supporting Tests and Shared Supporting Tests are advisory. They may be `nonblocking` or `disabled`. `required` is rejected, so those tests stay out of `test:features` and `test:gate`.

Nonblocking and disabled tests remain visible. Disabled tests are not executed by feature, suite, or release-gate commands. An explicit catalog test identifier, `npm run test:id -- FBT-133` or `npm run test:feature -- FBT-133`, runs that one test and still leaves it disabled for those other commands. A nonblocking pass is recorded as passed and stays outside the release gate. The catalog never presents disabled, deprecated, retired, or unexecuted as the primary passing result. Required inconclusive verification exits with code 2 and blocks a passed gate. Failure exits with code 1.

Live readiness, layer-settle, and hit-test timeouts are failures unless concrete evidence shows approved external-service unavailability, a network, Domain Name System (DNS), or Transport Layer Security (TLS) failure, HTTP (Hypertext Transfer Protocol) 429 or 5xx responses, or a graphics-environment failure. Timeout text alone, or `net::ERR_ABORTED` alone, stays a failure.

Lifecycle or legal non-default enforcement changes require a concise reason, affected behaviors, consequences, and approval evidence. Reactivation additionally requires a recorded expected-behavior review and restored required Feature Behavior verification. Preserve deprecated definitions, test metadata, and relevant implementation whenever reactivation remains plausible. Supporting Test failures still require investigation before a release is called verified.

## Fixtures, cache, and reports

Reviewed fixtures live in `tests/fixtures/recorded`, with source, version, checksum, review, and association metadata in `tests/fixtures/manifests`. Fixture refresh is manual: edit or replace the reviewed file, run `shasum -a 256 <fixture>`, update its manifest, and obtain review approval. No refresh automation is provided.

The ignored local cache defaults to `.test-cache`. Set `TNC_TEST_CACHE_DIR` to an absolute or shared cache location when multiple clones should reuse large local test assets. Generated browser artifacts, reports, latest results, and history remain under ignored local directories.

Live browser tests reuse saved live-service responses through the response cache in `tests/support/browser/response-cache/`. It holds two sources, one module each:

- Esri responses (`*.arcgis.com`, `*.arcgisonline.com`) in `.test-cache/esri-responses/v1`. The key is the request URL with tokens and `_ts` removed and the query sorted.
- USGS 3DEP (3D Elevation Program) terrain tiles in `.test-cache/usgs-3dep-responses/v1`. The page requests them from the same-origin dev-server proxy `/api/usgs-elevation/exportImage`, which forwards to `elevation.nationalmap.gov`. The key is the upstream USGS URL with the query sorted, so the page-server port never changes it.

Those locations honor `TNC_TEST_CACHE_DIR`. A response missing from the cache is fetched live and saved, and that miss never fails a test, so a new feature can add requests. HTTP 200 and 404 responses are saved. HTTP 429 and 5xx responses are not, and neither is a USGS HTTP 200 whose body is a JSON error. Replays return the saved status, content type, and exact body bytes. Tokens and `_ts` never reach the cache key or the disk. This cache is unrelated to the reviewed fixtures in `tests/fixtures/recorded`. A lint rule requires `*.live.spec.ts` files to import `test` and `expect` from `tests/support/browser/response-cache/index.ts`.

## Live browser rendering and test mode

The live Playwright project uses the `chromium` channel so WebGL (Web Graphics Library) runs on the GPU (graphics processing unit). First-time setup is `npx playwright install chromium`. A machine without a usable GPU falls back to SwiftShader and is slower, but it measures the same frames. The test web server sets `VITE_TEST_MODE=true`, which adds the `moveCamera` command to the page's read-only test seam. Normal `npm run dev` does not set that variable, so the command is absent. Scene tests move to fixed cameras and wait until the Esri SceneView has finished loading and the camera is still before checking a frame. A measured scene failure stays a failure even when Esri also returned HTTP 429 or 5xx.
